회차01 웹의 구성 요소
  1. 인터넷장현규
  2. 웹김유진
  3. 브라우저김수민
  4. HTML변진수
  • 개발 PC와 JBoss 서버는 사내망에서 서로 통신하지만 두 장비 모두 외부 인터넷에는 접속하지 못합니다. 이때 성립한 연결의 범위를 적고, 사내 네트워크 연결과 전 세계 인터넷 연결을 같은 말로 볼 수 없는 이유를 설명해 보세요.
  • 인터넷 선을 끊었는데도 개발 PC의 http://localhost에서 Vue 3 화면이 열립니다. 브라우저가 어느 장비의 웹 서버에 접속한 것인지 밝히고, 외부 인터넷을 거치지 않아도 HTTP 기반 웹 화면을 사용할 수 있는 이유를 설명해 보세요.
  • 같은 eXBuilder 화면 파일을 한 번은 공유 폴더에서 직접 열고, 한 번은 Apache의 URL로 열었습니다. 두 경우에 브라우저가 파일을 가져오는 경로와 사용하는 프로토콜을 각각 적고, Apache를 거친 경우만 웹 요청이라고 할 수 있는 이유를 설명해 보세요.
  • 사용자는 Vue 3 주소 하나만 입력했지만 Apache 로그에는 HTML, CSS, JavaScript 요청이 각각 남았습니다. 최초 HTML을 받은 뒤 브라우저가 추가 파일의 주소를 어떻게 알아내는지, 왜 파일마다 별도 요청을 보내는지 순서대로 설명해 보세요.
  • JBoss 연결이 끊긴 뒤에도 eXBuilder 화면의 메뉴와 입력 칸은 보이지만 조회 버튼을 누르면 실패합니다. 화면에 남은 파일은 어디서 이미 받은 것인지, 조회할 때 새로 받아야 하는 데이터는 어디에서 오는지 나눠 설명해 보세요.
  • Vue 3 화면에서 버튼을 눌렀더니 서버 통신 없이 접힌 영역만 펼쳐졌습니다. 개발자 도구에서 어떤 네트워크 기록을 확인해야 하는지 적고, 요청이 없다면 JavaScript가 DOM을 바꾼 동작이라고 판단할 수 있는 이유를 설명해 보세요.
  • 같은 HTML 파일을 file:// 주소와 Apache의 https:// 주소로 각각 열었습니다. 두 주소에서 상대 경로의 기준과 브라우저가 판단하는 출처가 어떻게 달라지는지 적고, 그 차이가 보안 정책에 영향을 주는 이유를 설명해 보세요.
  • 개발자는 eXBuilder 개발 도구에서 화면을 작성했고, 사용자는 그 결과물을 브라우저에서 실행합니다. 화면을 만드는 도구와 사용자가 실행하는 파일의 역할을 각각 적고, 둘을 같은 프로그램이라고 부르면 실행 위치와 장애 원인을 왜 잘못 판단하게 되는지 설명해 보세요.
  • 브라우저에는 HTML과 CSS로 만든 화면이 정상적으로 보이지만 eGovFrame 조회만 실패합니다. 이 결과로 브라우저와 Apache의 어떤 기능까지 정상이라고 확인할 수 있는지 적고, Apache의 API 전달과 JBoss 처리는 왜 별도로 확인해야 하는지 설명해 보세요.
  • 사용자가 Vue 3에서 조회 버튼을 누르자 Tibero의 데이터가 화면에 표시됐습니다. 웹이 제공한 통신 방식, 브라우저가 실행한 화면 코드, HTML이 표현한 문서 구조를 각각 적고, 세 개념이 조회 흐름에서 맡은 역할을 구분해 설명해 보세요.
회차02 웹 애플리케이션의 역할
  1. 클라이언트장현규
  2. 서버김유진
  3. 프론트엔드김수민
  4. 백엔드변진수
  • Vue 3와 eXBuilder는 사용자에게 보이는 화면을 구성하는 프론트엔드이며, eGovFrame API에 요청을 보내는 클라이언트이기도 합니다. ‘화면을 담당한다’는 분류와 ‘요청을 보낸다’는 분류가 각각 무엇을 기준으로 하는지 적고, 두 용어가 항상 같은 대상을 뜻하지 않는 이유를 설명해 보세요.
  • 모바일 앱이 eGovFrame API에 요청을 보내지만 Vue 3나 eXBuilder로 만든 웹 화면은 아닙니다. 이 앱을 클라이언트라고 부를 수 있는 근거를 적고, 웹 프론트엔드라고 부르기 어려운 이유를 실행 환경과 사용자 화면 기술 기준으로 설명해 보세요.
  • Apache는 Vue 3 정적 파일을 브라우저에 보내고 API 요청은 JBoss로 전달합니다. Apache가 서버로 동작하는 두 경우를 적고, 이 역할을 eGovFrame의 업무 규칙을 실행하는 백엔드 역할과 구분해야 하는 이유를 설명해 보세요.
  • JBoss 안에서 eGovFrame 애플리케이션이 실행되고 있습니다. JBoss가 관리하는 실행 환경과 eGovFrame 코드가 처리하는 업무 로직을 각각 적고, 둘을 모두 ‘백엔드’라고만 부르면 장애 원인과 수정 대상을 어떻게 혼동할 수 있는지 설명해 보세요.
  • 현장에서는 Tibero가 설치된 물리 장비, 실행 중인 Tibero DBMS 프로세스, 그 안에 생성한 데이터베이스를 모두 ‘DB 서버’라고 부르기도 합니다. 세 대상을 각각 구분해 적고, 접속 실패와 SQL 실패를 조사할 때 이 구분이 필요한 이유를 설명해 보세요.
  • eXBuilder 화면 코드는 사용자 브라우저에서 실행되고 eGovFrame 코드는 JBoss에서 실행됩니다. API 요청을 보내는 프로그램과 요청을 받아 업무를 처리하는 프로그램을 각각 클라이언트와 서버로 분류하고, 실행 위치가 이 분류에 어떤 근거가 되는지 설명해 보세요.
  • Vue 3 화면이 입력값으로 금액을 계산한 뒤 eGovFrame도 같은 금액을 다시 계산하고 검증합니다. 사용자가 브라우저의 값이나 요청 내용을 바꿀 수 있다는 점을 설명하고, 최종 저장 전에 서버 검증이 반드시 필요한 이유를 적어 보세요.
  • 조회 요청은 브라우저 → Apache → JBoss의 eGovFrame → Tibero 순서로 전달됩니다. 각 화살표에서 요청을 보내는 쪽을 클라이언트, 받는 쪽을 서버로 짝지어 적고, 같은 Apache나 JBoss가 구간에 따라 두 역할을 모두 가질 수 있는 이유를 설명해 보세요.
  • Apache가 Vue 3 화면 파일은 정상적으로 보냈지만 조회 데이터는 표시되지 않습니다. 정적 화면 표시가 성공했다는 사실로 확인된 구성 요소를 적고, JBoss의 eGovFrame 처리까지 성공했다고 판단할 수 없는 이유를 설명해 보세요.
  • 한 번의 조회가 브라우저 요청, Apache 전달, eGovFrame 처리, Tibero 조회 중 한 단계에서 실패했습니다. 브라우저 네트워크 기록부터 Apache·JBoss 로그와 Tibero 실행 기록까지 어떤 순서로 비교할지 적고, 그 순서로 실패 구간을 좁힐 수 있는 이유를 설명해 보세요.
회차03 네트워크 연결
  1. IP김수민
  2. DNS장현규
  3. 포트변진수
  4. TCP/UDP김유진
  • Vue 3 화면에서 조회 버튼을 누르면 요청은 브라우저 → Apache → JBoss → Tibero 순서로 이동합니다. 각 화살표마다 요청을 보내는 장비의 IP와 요청을 받는 장비의 IP를 적고, 한 번의 조회인데도 구간마다 출발지와 목적지가 달라지는 이유를 설명해 보세요.
  • eGovFrame API 주소를 localhost로 설정했더니 JBoss 서버에서는 호출되지만 eXBuilder를 실행한 사용자 PC에서는 실패했습니다. localhost가 현재 코드를 실행하는 장비를 가리킨다는 점을 기준으로, 두 환경에서 각각 어떤 장비를 찾는지 설명해 보세요.
  • 브라우저가 서비스 도메인을 조회하자 DNS는 Apache의 IP를 돌려줬습니다. DNS가 알려 준 대상과 범위를 적고, JBoss의 eGovFrame과 Tibero는 누가 어떤 주소 설정을 사용해 찾아가는지 구분해 설명해 보세요.
  • Apache를 새 IP로 옮긴 뒤 Vue 3 사용자는 새 서버에 접속하지만 eXBuilder 사용자는 이전 서버에 접속합니다. 두 PC에서 DNS가 돌려준 IP와 남은 TTL을 각각 확인해, 캐시에 남은 이전 주소 때문인지 판단하는 방법을 설명해 보세요.
  • 브라우저는 Apache의 443번 포트, Apache는 JBoss의 8080번 포트, JBoss는 Tibero의 8629번 포트로 연결됩니다. 각 연결에서 요청을 보내는 프로그램과 받는 프로그램을 순서대로 적고, 같은 IP에서도 포트로 대상 프로그램을 구분해야 하는 이유를 설명해 보세요.
  • 외부 방화벽에는 Apache의 443번 포트만 열려 있고 JBoss의 8080번과 Tibero의 8629번은 외부에서 접근할 수 없습니다. 사용자의 조회 요청이 어느 프로그램을 거쳐 Tibero까지 도착하는지 순서대로 적고, 내부 포트를 외부에 열지 않아도 조회가 되는 이유를 설명해 보세요.
  • Apache 설정은 API 요청을 JBoss의 8180번 포트로 보내지만 JBoss는 8080번 포트에서만 기다리고 있습니다. 브라우저 → Apache와 Apache → JBoss 중 어느 연결까지 성공하는지 적고, 다음 연결이 실패하는 원인을 설명해 보세요.
  • DNS 조회는 UDP로 성공해 Apache의 IP를 받았지만, 그 IP의 443번 포트로 여는 TCP 연결은 시간 초과됐습니다. 이 결과로 DNS가 정상이라고 볼 수 있는 이유와 아직 확인되지 않은 Apache·방화벽 구간을 나눠 설명해 보세요.
  • 조회 버튼을 한 번 눌러도 브라우저–Apache, Apache–JBoss, JBoss–Tibero는 각각 별도의 TCP 연결을 사용합니다. 각 연결의 양쪽 프로그램을 적고, 앞 연결이 다음 연결까지 그대로 이어지는 하나의 통로가 아닌 이유를 설명해 보세요.
  • 브라우저가 JBoss에서 생성한 HTTP 500 응답을 받았습니다. 이 응답이 브라우저–Apache와 Apache–JBoss 통신 성공을 뜻하는 이유를 설명하고, eGovFrame 코드와 Tibero 처리 중 어디서 실패했는지는 이 정보만으로 결정할 수 없는 이유도 적어 보세요.
회차04 HTTP
  1. URL과 리소스
  2. 메서드와 멱등성
  3. 요청·응답 메시지와 상태 코드
  4. HTTP 캐시
  5. 헤더와 콘텐츠 협상
  • 같은 서비스 도메인에서 /assets/app.js 요청은 Apache가 파일로 응답하고, /api/users 요청은 JBoss의 eGovFrame으로 전달합니다. 두 URL에서 경로가 가리키는 리소스와 실제 처리 프로그램을 각각 적고, Apache가 이를 구분하는 설정도 설명해 보세요.
  • 사용자 목록을 요청할 때는 ?page=2처럼 페이지 번호를 쿼리에 넣고, 특정 사용자를 요청할 때는 사용자 번호를 URL 경로에 넣으려 합니다. 두 값이 각각 ‘조회 조건’과 ‘식별할 리소스’ 중 무엇을 나타내는지 적고, 경로와 쿼리를 그렇게 나누는 이유를 설명해 보세요.
  • GET 조회를 여러 번 실행하자 Apache와 JBoss의 접근 로그는 늘었지만 Tibero의 업무 데이터는 바뀌지 않았습니다. HTTP의 안전성과 멱등성이 어떤 데이터 변경을 기준으로 판단되는지 적고, 단순 로그 생성은 왜 그 성질을 깨지 않는지 설명해 보세요.
  • 사용자의 중복 클릭 때문에 같은 POST 저장 요청이 두 번 JBoss에 도착했습니다. Vue 3의 버튼 잠금, 요청 고유 번호를 이용한 eGovFrame 검사, Tibero의 고유 키가 각각 어느 단계에서 중복을 막는지 적고, 한 가지 방어만으로 충분하지 않은 이유를 설명해 보세요.
  • Apache가 POST 저장 요청을 다른 URL로 이동시키는 응답을 보내야 합니다. 302와 307·308 이후 브라우저가 사용할 수 있는 메서드와 본문을 비교하고, 원래 저장 요청을 유지하려면 뒤의 상태 코드를 써야 하는 이유를 설명해 보세요.
  • API 호출 결과로 404, 405, 502가 각각 발생했습니다. 요청한 경로나 리소스가 없는 경우, 해당 메서드를 받지 않는 경우, Apache가 JBoss에 연결하지 못한 경우에 알맞은 코드를 짝지어 적고 그 판단 근거를 설명해 보세요.
  • eXBuilder는 요청 헤더에 Content-Type: application/json을 넣고 저장할 값을 JSON 본문으로 보냈습니다. JBoss는 HTTP 200, 응답 헤더의 Content-Type: application/json, 업무 실패가 담긴 JSON 본문을 반환했습니다. 요청·응답의 헤더와 본문, 상태 코드가 각각 알려 주는 정보를 구분하고, 전송 성공과 eGovFrame의 업무 실패를 어떻게 판단할지 설명해 보세요.
  • Apache가 기다리던 시간 안에 JBoss 응답을 받지 못해 504를 보냈지만, JBoss는 이후 Tibero 저장을 완료했습니다. 브라우저가 받은 시간 초과와 서버 내부 작업의 종료 시점을 각각 적고, 재시도할 때 중복 저장 위험이 생기는 이유를 설명해 보세요.
