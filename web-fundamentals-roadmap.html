회차01 웹의 구성 요소
  1. 인터넷장현규
  2. 웹김유진
  3. 브라우저김수민
  4. HTML변진수
  • 노트북 두 대만 랜선으로 직접 연결해 파일을 주고받았습니다. 이 연결이 인터넷이 아닌 근거를 ‘네트워크’와 ‘인터넷’의 범위 차이로 설명할 수 있나요?
  • 인터넷 연결을 끊은 상태에서도 브라우저로 http://localhost의 Vue 화면에 접속할 수 있습니다. 인터넷을 사용하지 않았지만 웹 애플리케이션은 사용했다고 볼 수 있는 이유는 무엇인가요?
  • 외부 인터넷은 끊겼는데 사내 Apache 페이지는 열릴 수 있는 이유는 무엇인가요?
  • 브라우저가 eXBuilder 화면 파일을 이미 받은 뒤 서버 연결이 끊겼습니다. 화면 모양은 남아 있는데 새 데이터만 나오지 않는 이유를 ‘이미 받은 화면 파일’과 ‘서버에서 새로 받아야 하는 데이터’로 나눠 설명할 수 있나요?
  • HTML·CSS로 된 화면은 보이지만 새 데이터 조회만 실패합니다. 이 사실만으로 브라우저의 화면 렌더링, Apache의 정적 파일 응답, WildFly의 API 처리 중 어디까지 성공했다고 판단할 수 있나요?
  • 인터넷에 연결하지 않고 로컬 HTML 파일을 브라우저로 열었다면 인터넷·웹·브라우저·HTML 중 무엇을 사용한 것인가요?
  • 주소 하나를 입력했는데 Apache의 HTML 뒤로 CSS·JavaScript·이미지 요청이 따로 이어지는 이유는 무엇인가요?
  • SSR 화면과 CSR 화면은 모두 브라우저에 표시되는데, 최초 HTML을 완성하는 위치는 어떻게 다른가요?
  • eXBuilder 개발 도구와 eXBuilder로 만든 실제 화면 프로그램은 서로 다릅니다. 개발할 때 쓰는 도구와 사용자가 보는 화면이 각각 어디에서 실행되는지 설명할 수 있나요?
  • 버튼을 눌렀을 때 네트워크 요청 없이 화면만 바뀌었습니다. 서버가 새 HTML을 보낸 것이 아니라 브라우저의 JavaScript가 상태나 DOM을 변경한 것이라고 판단할 수 있는 근거는 무엇인가요?
회차02 웹 애플리케이션의 역할
  1. 클라이언트장현규
  2. 서버김유진
  3. 프론트엔드김수민
  4. 백엔드변진수
  • ‘클라이언트’는 요청을 보내는 쪽이고, ‘프론트엔드’는 사용자가 보는 화면을 만드는 영역입니다. 그렇다면 클라이언트와 프론트엔드는 언제 같은 대상을 가리키고 언제 다른가요? 서버와 백엔드도 같은 방식으로 설명해 보세요.
  • Vue는 프론트엔드 기술이자 클라이언트에서 실행되는 프로그램인가요? eXBuilder는 어떤가요? 기술·개발 도구·실행 결과물을 구분해 각각의 이유를 설명해 보세요.
  • 브라우저 요청을 받은 Apache는 브라우저에 대해서는 서버이지만, 같은 요청을 WildFly로 전달할 때는 클라이언트가 됩니다. 한 프로그램이 연결마다 두 역할을 가질 수 있는 이유는 무엇인가요?
  • Tibero는 넓게 보면 백엔드에 속하고, 정확한 기술 종류는 DBMS(데이터베이스 관리 프로그램)입니다. ‘백엔드’, ‘Tibero 프로그램’, ‘Tibero에 저장된 데이터베이스’는 각각 무엇을 뜻하나요?
  • 화면 파일은 열리지만 데이터가 나오지 않습니다. 브라우저의 요청 내역 → Apache 기록 → WildFly·eGovFrame 기록 → Tibero 접속 상태 순으로 무엇을 확인해야 문제가 생긴 구간을 찾을 수 있나요?
  • CSR에서는 Vue 코드가 브라우저에서 화면을 만들고, SSR에서는 서버가 HTML을 만든다고 할 때 각각의 클라이언트와 서버 역할은 무엇인가요?
  • Vue를 SSR로 실행하면 Vue가 더 이상 프론트엔드 기술이 아니게 되나요? 실행 위치와 담당 역할을 나눠 설명해 보세요.
  • Apache는 Vue·eXBuilder 화면 파일을 보내고, 데이터 요청은 WildFly로 넘깁니다. Apache를 화면을 만드는 프론트엔드나 업무를 처리하는 백엔드가 아니라 ‘웹 요청을 받아 전달하는 서버 프로그램’으로 보는 이유는 무엇인가요?
  • WildFly와 eGovFrame을 모두 백엔드라고 부를 수 있더라도 두 기술의 역할은 어떻게 다른가요?
  • 별도 컴퓨터에서 Tibero가 실행됩니다. ‘DB 서버’는 ① Tibero가 설치된 컴퓨터, ② SQL 요청을 처리하는 Tibero 프로그램을 뜻할 수 있습니다. 둘은 어떻게 다른가요? 테이블과 데이터 자체를 뜻하는 ‘데이터베이스’는 또 무엇이 다른가요?
회차03 네트워크 연결
  1. IP
  2. DNS
  3. 포트
  4. TCP/UDP
  • 하나의 IP 주소에서 Apache와 WildFly가 함께 실행되는데도 포트가 필요한 이유는 무엇인가요?
  • DNS가 도메인을 IP 주소로 바꿔줬다면 원하는 WildFly 프로그램까지 찾아준 것인가요?
  • localhost와 127.0.0.1은 인터넷에 있는 다른 서버를 뜻하나요?
  • 브라우저–Apache 연결과 Apache–WildFly 연결은 하나의 TCP 연결인가요, 서로 다른 연결인가요?
  • 도메인은 IP로 잘 바뀌지만 접속이 거부된다면 DNS가 고장 난 것이라고 볼 수 있나요?
  • http://localhost:8080 화면이 http://localhost:8081 API를 호출합니다. 주소의 방식(http)과 컴퓨터 이름(localhost)은 같지만 포트가 다르므로 브라우저가 서로 다른 출처로 보는 이유는 무엇인가요?
  • 사내 IP를 쓰는 개발 PC가 인터넷 공유기를 거쳐 운영 서버에 접속합니다. NAT는 개발 PC의 내부 주소를 외부에서 쓸 주소로 바꾸고, DNS는 도메인 이름을 IP 주소로 찾습니다. 두 기능은 어떻게 다른가요?
  • TCP 연결은 성공했지만 WildFly가 HTTP 500 오류를 보냈습니다. 이때 ‘서버까지 데이터를 주고받는 연결’은 성공했고 ‘서버의 업무 처리’는 실패했다고 나눠 말할 수 있는 이유는 무엇인가요?
  • 브라우저–Apache와 WildFly–Tibero 연결에는 주로 TCP를 사용합니다. TCP가 데이터를 보낸 순서대로 전달하고, 중간에 빠진 데이터는 다시 보내 주는 것이 왜 중요한가요?
  • 같은 도메인을 조회했는데 사용자마다 다른 IP 주소가 나옵니다. 예전에 저장된 DNS 정보 때문인지, 여러 서버로 접속을 나누는 정상 동작인지 구분하려면 각 PC가 받은 IP 주소와 그 정보의 남은 저장 시간(TTL)을 어떻게 비교해야 하나요?
회차04 HTTP
  1. URL과 리소스
  2. 메서드와 멱등성
  3. 상태 코드와 메시지
  4. HTTP 캐시
  • 404 응답을 받았다면 서버 연결에 실패한 것인가요, 서버가 답을 준 것인가요?
  • eGovFrame API가 HTTP 200과 함께 { "success": false }를 보냈습니다. 서버와 통신한 것은 성공했지만 실제 업무 처리는 실패한 상황입니다. 화면에서는 HTTP 상태와 응답 내용 중 무엇을 함께 확인해야 하나요?
  • 같은 조회 요청(GET)을 여러 번 보내는 경우와 같은 저장 요청(POST)을 여러 번 보내는 경우를 비교해 보세요. 여러 번 실행해도 서버 데이터의 최종 결과가 같은 ‘멱등성’은 두 요청에서 어떻게 다른가요?
  • Apache가 200으로 CSS를 보냈는데도 예전 화면이 보인다면 HTTP 캐시부터 확인해야 하나요? 그 이유는 무엇인가요?
  • Apache 화면은 열리지만 API에서 502가 나온다면 WildFly와의 연결을 의심하는 이유는 무엇인가요?
  • GET은 안전하고 멱등하다고 하는데, 조회 API를 호출할 때마다 서버 로그가 쌓여도 이 원칙을 지킨 것인가요?
  • 저장 버튼을 두 번 눌러 같은 요청이 반복됐습니다. 화면에서 두 번째 클릭을 막는 방법, 서버에서 같은 요청인지 구별하는 고유 번호를 쓰는 방법, Tibero에서 중복 값을 허용하지 않는 방법은 각각 어느 단계에서 중복 저장을 막나요?
  • 로그인 쿠키나 인증 헤더가 빠진 요청이 Apache까지 도착했다면 401과 403 중 어떤 응답이 더 알맞은가요?
  • 브라우저가 저장해 둔 파일의 버전 표시(ETag)를 서버에 보냈고, 서버는 파일이 바뀌지 않았다는 304 응답을 보냈습니다. 브라우저는 새 파일과 저장해 둔 파일 중 어느 것을 사용하나요?
  • SSR에서는 서버가 데이터를 가져오다 실패했고, CSR에서는 브라우저가 데이터를 가져오다 실패했습니다. 각각 서버 기록과 브라우저 요청 내역 중 어디에서 오류를 찾을 수 있으며, 사용자가 보는 화면은 어떻게 달라질까요?

  • Vue의 조건부 렌더링으로 제목처럼 보이는 요소를 만들 때도 h1부터 h6까지의 문서 구조를 지켜야 하는 이유는 무엇인가요?
  • SSR이 만든 HTML과 CSR이 나중에 만든 HTML 모두 시맨틱 규칙과 접근성을 지켜야 하는 이유는 무엇인가요?

회차20 빌드·배포·운영
  1. Maven과 의존성
  2. Jenkins 파이프라인
  3. Apache·WildFly 배포
  4. 환경 설정·모니터링·롤백
  • Maven이 소스 코드를 검사하고 실행 파일로 묶는 빌드에 성공했습니다. 이것만으로 새 프로그램이 WildFly에 배포되어 실행 중이라고 볼 수 없는 이유는 무엇인가요?
  • Jenkins 작업이 성공으로 끝나도 배포 단계가 빠져 있었다면 운영 코드는 바뀔까요?
  • Vue·eXBuilder 결과물은 Apache가 그대로 보내는 화면 파일이고, eGovFrame 결과물은 WildFly가 실행하는 묶음 파일(WAR)입니다. 두 파일은 배포 위치, 이전 파일이 남는 캐시 처리, 서버 재시작 필요 여부가 어떻게 다른가요?
  • Apache를 재시작하지 않고 정적 파일만 바꾼 경우와 WildFly에 새 애플리케이션을 올린 경우는 무엇이 다른가요?
  • 새로 배포했는데 일부 사용자만 예전 화면을 본다면 서버 배포와 브라우저 캐시 중 어느 쪽 문제인지 어떻게 구분할까요?
  • Jenkins가 만든 WAR 파일과 WildFly에 실제 올라간 파일이 완전히 같은지 확인하려고 파일의 고유한 계산값(hash)을 비교합니다. 이를 통해 어떤 잘못된 배포를 찾을 수 있나요?
  • 개발·검증·운영의 Tibero 주소와 비밀 값을 WAR 안에 넣지 않고 외부 설정으로 분리해야 하는 이유는 무엇인가요?
  • WildFly를 한 대씩 새 버전으로 바꾸는 동안 이전 코드와 새 코드가 같은 Tibero 테이블을 함께 사용합니다. 테이블을 바꿀 때 이전 코드도 계속 작동하도록 해야 하는 이유는 무엇인가요?
  • 배포 직후 첫 주소가 열린 것만 확인하면 충분할까요? 실제로 Apache에서 WildFly를 거쳐 Tibero 조회까지 해 보는 상태 점검과 로그·속도·오류 수치는 무엇을 더 알려주나요?
  • 프로그램 파일은 이전 버전으로 되돌렸지만 Tibero 테이블 구조는 이미 새 버전에 맞게 바뀌었습니다. 프로그램 파일만 되돌려서는 복구되지 않을 수 있는 이유는 무엇인가요?
보너스회차 생성형 AI와 웹 개발
  1. 생성형 AI와 LLM
  2. 프롬프트·토큰·컨텍스트·환각
  3. 클라우드 AI와 API
  4. 로컬 LLM과 Ollama
  • ChatGPT는 사용자가 이용하는 AI 서비스이고, LLM은 글을 이해하고 만드는 AI 모델의 종류이며, Ollama는 AI 모델을 내 PC에서 실행하는 도구입니다. 세 이름이 같은 대상을 뜻하지 않는 이유는 무엇인가요?
  • Vue 화면에서 클라우드 AI를 바로 호출하면 비밀 접속 키(API 키)가 브라우저에 드러날 수 있습니다. 요청을 eGovFrame과 WildFly가 대신 보내게 하면 키를 숨길 수 있는 이유는 무엇인가요?
  • eGovFrame과 WildFly가 클라우드 AI에 질문을 보내고 답을 받는 과정도, 다른 서버 API처럼 HTTP 요청과 응답으로 이루어진다고 볼 수 있는 이유는 무엇인가요?
  • 내 PC의 localhost:11434에서 Ollama가 실행됩니다. localhost는 ‘현재 사용 중인 내 컴퓨터’를 뜻하므로 다른 팀원의 PC에서는 같은 주소로 접속할 수 없는 이유는 무엇인가요?
  • 클라우드 AI만 응답하지 않는다면 인터넷 연결·접속 키·외부 서비스 상태를 확인해야 하고, Ollama만 응답하지 않는다면 내 PC의 프로그램 실행 여부와 포트를 확인해야 합니다. 확인 대상이 다른 이유는 무엇인가요?
